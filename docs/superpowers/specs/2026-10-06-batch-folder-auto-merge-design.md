# Batch Folder Auto-Merge Design

**Date:** 2026-10-06

## Goal

Extend the existing **Batch Folder** flow so each complete part pair is rendered
and then merged automatically. A scan of a leaf folder containing
`<lesson>_1` and `<lesson>_2` creates two slide-render jobs followed by one
dependent merge job. The merge must use the outputs produced by that same scan,
not stale files or jobs from an earlier scan.

The workflow remains recursive over leaf folders and keeps the existing naming,
timeline, logo, and part-2-only outro rules.

## Input grouping and naming

- A valid part keeps the current three-file contract: a PPTX ending in `_1` or
  `_2`, media with the same stem, and a direct or `timeline_slide_` timeline.
- Parts are paired only when they are in the same leaf folder and their stems
  differ only by the final `_1`/`_2` suffix.
- A leaf folder may contain more than one independent lesson pair; each exact
  base name is handled separately.
- The part outputs remain:
  `output/<lesson>_1.mp4` and `output/<lesson>_2.mp4`.
- The merged output removes the part suffix: `output/<lesson>.mp4`.
- Part 1 is always the first merge input and part 2 is always the second.

If only one valid part exists, that part is still queued for rendering. No merge
job is created, and the scan reports that the other part is missing. Invalid or
ambiguous inputs continue to be reported per leaf folder without blocking valid
jobs elsewhere.

## Job dependency model

`JobRecord` gains a persisted `dependency_job_ids` collection. Existing saved
jobs that lack this field load with no dependencies, preserving compatibility.
The field is general queue metadata, but this feature initially uses it only for
Batch Folder merge jobs.

Each complete pair queues an isolated group in this order:

1. Render part 1.
2. Render part 2.
3. Merge the two rendered outputs, depending on both render job IDs.

Every **Scan & Add** creates a new group with new IDs, even if identical jobs or
outputs already exist. Consequently, the merge job can only become runnable
after both render jobs from its own scan have completed. File existence alone
never satisfies a dependency.

The queue scheduler applies these rules:

- All dependencies completed: validate the merge inputs and claim the job.
- Any dependency waiting, running, failed, or interrupted: keep the merge job
  waiting. Retrying and completing the failed/interrupted part automatically
  makes the merge eligible without a separate merge retry. Because repeated
  scans intentionally share the same three public output paths, retrying or
  auto-restoring one batch part requeues both parts and their merge together;
  both inputs are regenerated by that scan group before its merge is claimed.
- A referenced dependency no longer exists: fail the merge job with a clear
  missing-dependency error.
- A waiting job that is still referenced by a waiting dependent cannot be
  removed. The UI tells the user to remove the dependent merge job first.

The scheduler may skip a blocked merge and continue with unrelated waiting jobs,
so a failed part does not stop other lessons. Dependencies and statuses survive
application restarts through `jobs.json`. Existing startup recovery continues to
mark interrupted running jobs, leaving their dependent merge jobs waiting for a
successful retry.

## Batch merge behavior

Manual jobs from **Add job** and **Merge 2 videos** keep their current behavior:
they reject an existing output and create a report JSON. Batch render and batch
merge jobs instead use:

- `overwrite_output=True`
- `write_report=False`

The merge pipeline receives these settings from the job just as the slide
pipeline does. It renders and verifies a staged video under the destination
filesystem, then atomically replaces an existing merged output only after
verification succeeds. Failure or cancellation preserves the previous merged
video. No batch `*.report.json` remains.

All three successful MP4 files are retained:

```text
output/
  <lesson>_1.mp4
  <lesson>_2.mp4
  <lesson>.mp4
```

The part-2 render already contains the configured outro, so the merge operation
does not add another outro. Part 1 remains without an outro. The configured logo
continues to apply to both rendered parts.

## Queue and UI behavior

The Batch Folder guide documents the input pair, merged output naming, retained
three-file layout, and part-2-only outro rule. The scan result count includes
both render and merge jobs. The common queue displays the dependent merge as a
normal `merge` row after its two `slide` rows.

A dependency-blocked merge remains visibly `waiting`; it is not marked as
missing merely because its future part outputs do not exist yet. Once the two
render jobs complete, the worker proceeds automatically. Retrying a part wakes
the worker through the existing UI action.

No new toggle is added: automatic merge is the standard behavior for every
complete pair scanned through **Batch Folder**. The standalone merge tab remains
available for unrelated manual merges.

## Failure and recovery cases

- Part render failure: preserve any old part output and keep its merge waiting.
- Part retry succeeds: merge becomes eligible automatically.
- Merge failure or cancellation: preserve the old merged output and both part
  outputs.
- Application closes during a part or merge: startup recovery marks only the
  running job interrupted; dependent merge stays waiting.
- A completed part output is deleted before merge claim: merge path validation
  fails explicitly rather than using another file or stale history.
- Re-scan after any status: enqueue a fresh pair and merge group whose dependency
  IDs cannot be satisfied by prior groups.

## Compatibility and scope

The JSON schema remains backward-compatible by defaulting missing dependency and
batch flags. The implementation must work on the supported Linux and Windows
setups and use the existing FIFO worker; it does not introduce parallel renders.

This change does not merge incomplete pairs, delete part outputs, add an outro
inside the merge pipeline, infer pairs across folders, or change the standalone
manual merge contract.

## Verification

Automated tests cover:

- exact `_1`/`_2` grouping and merged output naming;
- multiple independent pairs in one leaf folder;
- single-part rendering plus the missing-part warning;
- queue order and dependency isolation across repeated scans;
- blocked merges being skipped while unrelated jobs continue;
- failed/interrupted part retry making merge runnable;
- missing dependency and protected dependency removal behavior;
- JSON round-trip and migration of jobs without dependency metadata;
- application restart recovery with waiting dependent merges;
- batch merge propagation of overwrite/report settings;
- successful safe replacement, failure/cancellation preservation, and absence of
  batch reports;
- UI guide, status summary, and dependency-aware file readiness;
- preservation of standalone slide and merge behavior.

The full unit and integration test suite must pass. After implementation, the
running Linux UI is restarted so it loads the new code; Windows behavior is
covered by platform-safe paths and the existing Windows packaging/setup flow.
